## 📐 The ODC Automation Test Pyramid

To maintain a fast and reliable test suite, you must assign test cases to the lowest possible layer that can thoroughly verify the requirement:

```
        ▲
       / \
      /E2E\       <-- High-cost, Slow: Full browser journeys (e.g., Sequential approval workflow, manual PDF verification)
     /=====\
    /  API  \     <-- Medium-cost: JSON Push API, Straight Through Processing (STP) endpoints, downstream syncing
   /=========\
  / Database  \   <-- Medium-low: Direct PostgreSQL assertions for status updates, LEI lookups, user email retrieval
 /=============\
/     Unit      \ <-- Lowest-cost, Fast: Regex patterns, string normalization, helper math calculations, date limits
-----------------
```

### Allocation Rules:
1. **Pure Data Logic & Rules** (e.g. Group name character count, String casing, Date-in-future boundary validation) -> **Unit / Model Validation**.
2. **Database Integrity & Constraints** (e.g. Cascading deletes of LEIs, user email lookups) -> **Database direct SQL tests**.
3. **STP Integration / Downstream Systems** (e.g. JSON Push payload formatting, status code checking, API connectivity) -> **API / Integration layer**.
4. **End-to-End Core Journeys** (e.g. Creating approval group -> assigning to matrix -> submitting Document Framework -> completing parallel approval review) -> **E2E Browser (Serenity BDD + WebDriver)**.

## Output Document Format

Compile the final analysis and write it directly to **`docs/test-strategy.md`** (which will be consumed by the `/generate-tests` and `/review-tests` skills). Include the following sections:

### 1. Strategy Executive Summary
- **Scope analyzed:** Core features / target modules.
- **Pyramid Distribution Table:**
  | Testing Layer | Scenario Count | Focus / Scope | Target Execution Time |
  |---------------|----------------|---------------|-----------------------|
  | E2E Browser   | N              | Critical flow | < 3 mins              |
  | API           | N              | Payload / STP | < 10 secs             |
  | Database      | N              | Integrity     | < 5 secs              |
  | Unit          | N              | Boundary logic| < 1 sec               |

### 2. Detailed Test Cases Allocation Table
For every test case (TC-NNN) from `docs/test-scenarios.md`, specify:
- **Test ID & Title:**
- **Assigned Layer:** (Unit | Database | API | E2E Browser)
- **Technical Target:** (e.g. class name, REST endpoint, PostgreSQL query statement, or specific Page Object and Gherkin file)
- **Architectural Rationale:** Justify why this layer is sufficient and optimal, referencing locator stability and wait strategies from `serenity-best-practices`.

### 3. Code Reuse & Anti-Duplication Strategy
Detail how existing step definitions, page objects, locators, and utility functions in the codebase will be reused to avoid test code duplication:
- Identify overlapping steps in existing step definition classes.
- Describe shared locator strategies (e.g. mapping header elements to a single shared Page Object).
- Standardize on shared Gherkin keywords to map to established step bindings.

### 4. Anti-Patterns Flagged
Highlight any inefficient testing designs found in existing or requested tests, such as:
- **E2E Over-Testing:** Running full browser steps just to verify a text label, status code, or database constraint that can be tested in 1 second at the unit/database layer.
- **Ice Cream Cone:** An inverted pyramid where there are no Unit or Database checks, and everything is routed through heavy Selenium browser sessions.
- **Lack of Database Checks:** Relying on UI tables to verify record additions or cascading deletes, rather than running a direct PostgreSQL query check.
- **Flaky Thread Sleeps:** Using `Thread.sleep()` in test loops. Enforce `WebElementFacade` auto-waiting and expected conditions.
